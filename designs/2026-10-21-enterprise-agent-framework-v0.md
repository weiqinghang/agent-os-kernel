# 企业 Agent 通用框架 · v0 架构意见（一页）

- 目标：MVP「五脏俱全但每块可简陋」——层都在，实现极瘦
- 非目标：Agentic CI；Legacy Migration Agent；平台化 RBAC/多租户中台
- 原则：场景逻辑进 Skill；框架只保证「能跑、能停、能审、能看」

---

## 1) 模块边界

| 进**框架内核**（所有 Agent 共用、禁止塞业务） | 进 **Skill**（可热插、可换） | **永远留给人**（不做进框架） |
| --- | --- | --- |
| **Orchestrator**：按 Run 状态机推进；调度一步「想→调工具→等 HITL」 | 任务目标与成功标准；步骤剧本（拉什么源、问什么） | 产品该不该做、优先级、审美终审 |
| **Runtime**：一次 Run 的执行循环、超时、取消、重试预算 | Prompt / 少量场景校验 | 账号开通、密钥轮换政策、合规签字 |
| **Context**：Run 级工作记忆（消息、工具结果摘要、引用指针）；持久化最小：run_id + 事件日志 | 领域检索策略、分块、知识卡 schema | 「公司真理」仲裁（哪份文档为准） |
| **Tool Gateway**：统一工具调用口（MCP/HTTP）；鉴权透传；超时/错误归一 | 具体工具适配（Gmail、知识库、Git…） | 生产写权限的常开（默认关） |
| **Model Broker**：选模、打调用、记 usage 钩子；无业务路由表 | 该任务用哪类模型的**建议**（可覆盖） | 预算签字、供应商合同 |
| **Policy**：能力开关（只读/需 HITL/禁外发）；按 Run 声明，不按「企业角色矩阵」 | 场景额外约束（如「评论前必须 HITL」） | 组织级权限模型、审批流引擎 |
| **Observability**：run 事件流、工具/模型 span、关联 id；可 grep 的结构化日志 | 场景业务指标 | 全公司可观测平台建设 |
| **HITL**：暂停点、人回执 schema、恢复/拒绝 | 人审什么字段、文案 | 代替人做不可逆决定 |

**硬边界**：内核不得出现「Radar / 知识卡 / MR 评论 / 四角色狗粮」专有名词与表结构。出现即污染，打回 Skill。

## 2) 一次 Agent Run · 最小状态机

```text
created
  → planning          # 可选极瘦：生成/确认本轮步骤清单
  → acting            # 调模型 + Tool Gateway（可循环，受步数/时限预算）
  → awaiting_hitl     # 需要人时必经；不需要则跳过
  → acting | completed | failed | cancelled
  → completed         # 成功终态（产出物指针进 Context/外部系统由 Skill 写）
  → failed            # 不可恢复错误 / 预算耗尽
  → cancelled         # 人取消或上游取消
```

规则（可执行）：

1. **唯一活跃态**；每次进入 `awaiting_hitl` 必须带 `resume_token` + 待审 payload。
2. `acting` 内：`model → (tool*) → model` 闭环；工具失败可重试，耗尽则 `failed` 或升 HITL（Skill 声明）。
3. **禁止**内核实现「多 Agent 聊天室」；多角色＝多个 Run 或一个 Run 内多次 Skill 步骤，由 Orchestrator 编排，状态仍是这一套。
4. 持久化最小：`runs(id, status, skill_id, policy_json, created_at)` + `run_events(append-only)`。其余以后再说。

## 3) v0 默认形态

**默认：一个可部署单体**（一个进程/一个服务），内核八层用**包边界**切开，不要微服务。

| 拆 | v0 |
| --- | --- |
| 部署 | 1 服务 + 1 DB（或 SQLite/Postgres 均可，先一种） |
| 队列 | 可无；HITL 用 DB 状态 + 轮询/webhook 回执即可 |
| 模型 | Model Broker 内调 1～2 个提供商；不搞模型网格 |
| 工具 | Tool Gateway 进程内适配器；MCP 当客户端连外部 |
| 何时才拆 | 有第二条生产 Skill **且**出现独立扩缩/故障域需求；现在拆＝过度工程 |

狗粮（候选 D）可以**同进程多 Skill 角色**，不要四个服务。

## 4) 四候选 · 架构可验证性打分

维度（各 1–5，权重：验底座 > 覆盖层数 > 低污染）：

- **底座覆盖**：能否逼出 Orchestrator/Runtime/Context/Tool/Model/Policy/Obs/HITL
- **污染风险**：场景逻辑是否容易漏进内核（越高越差，表中用「洁净」分，越高越好）
- **HITL 真实性**：是否有不可跳过的人审（框架 HITL 是否被当真用）
- **v0 成本**：接入工具/数据是否可控

| 候选 | 底座 | 洁净 | HITL | 成本 | **总分** | 一句话 |
| --- | --- | --- | --- | --- | --- | --- |
| **A 情报 Radar** | 5 | 3 | 5 | 3 | **16** | 端到端最全（拉源→筛→HITL→入库），但「筛选/知识卡」易诱使内核长业务表 |
| **B 企业知识问答** | 4 | 4 | 4 | 4 | **16** | Tool+Context+引用+HITL 沉淀很干净；对 Orchestrator 多步压力略弱 |
| **C 研发只读助理** | 4 | **5** | 5 | 3 | **17** | **只读+HITL 后外发**最能验 Policy/HITL；场景边界清晰，污染最低 |
| **D 狗粮编排** | 3 | 2 | 3 | 5 | **13** | 验「多角色编排」好看，但易把主控/人事逻辑写进 Orchestrator，**最脏**；且不充分逼 Tool Gateway |

### 建议（可执行）

1. **v0 主验候选：C**（研发只读助理）。理由：强制 Policy（禁自动写代码/禁未审评论）+ 真 HITL + Context（Issue/MR）+ Tool Gateway（SCM 只读）+ Model + Obs；Skill 边界清楚，最不易污染内核。
2. **并行薄狗粮：用 B 作第二 Skill**（同单体），补「检索→带引用作答→HITL 沉淀」，加固 Context/引用而不引入 Radar 的入库领域模型。
3. **A 放到 v0.1**：等内核冻结后再做「入库」类 Skill，避免知识卡 schema 渗进框架。
4. **D 不要当 v0 验底座**：可当演示编排剧本（多个 C/B 式 Run 串起来），**禁止**为此扩展内核状态机成「四角色工作流引擎」。
